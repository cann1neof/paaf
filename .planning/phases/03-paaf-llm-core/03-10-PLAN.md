<objective>
Close **Gap 2** from `03-VERIFICATION.md` (status `failed`, classified 🛑 Blocker): `EngineError`
escapes `paaf chat` as a raw traceback, reproduced live twice by the verifier.

`_chat_loop` (`cli.py:244-247`) catches only `AllProvidersFailed`. `EngineError` — by the
adapter module's own docstring the class for the most likely real-world first-run failure (a
missing or unresolvable credential, a wrong model name), deliberately *not* an `AdapterError`
so the fallback loop cannot swallow it — propagates out of `asyncio.run` untouched. The same
hole covers a post-first-token-commit `AdapterError`, which the turn loop intentionally does
not catch once a profile has committed (`agent.py:287-291`).

There is a structural reason this was never fixable in place: `EngineError` is defined inside
the adapter package, which raises `ImportError` when the optional `[engine]` extra is absent.
A framework-free CLI therefore *cannot* name it in an `except` clause. So the fix is not a
`try` block — it is moving the type to where it always belonged. `EngineError` is already
documented as "PAAF-typed on purpose (no framework exception escapes the port)"; this plan
puts it in the port module that statement describes.

Purpose: for a phase whose thesis is "nothing hidden from the user, readable output", a
traceback on the headline command is the one failure mode that contradicts it outright.

Output: `EngineError` as a first-class port type, and three named failure surfaces on
`paaf chat` — bind failure, mid-reply failure, and chain exhaustion — each with a negative
control proving the handler did not become a catch-all.
</objective>
