**I want to** point a named profile at `http://192.168.1.20:8000/v1` and have `paaf chat` use it,
**so that** the "OpenAI-compatible endpoints" leg of SC#2 is a working configuration rather than
a theoretical one.

<objective>
Close **Gap 3** from `03-VERIFICATION.md`. Per the operator's decision (D-G2) this is fixed in
Phase 3 rather than recorded as an accepted limitation.

The verifier's finding, in three parts. `_engine/__init__.py:326-346` derives
`scheme://host:port` with no path; `paaf_core.net.endpoint.Endpoint` has no path field and
`ModelProfile` sets `extra="forbid"`, so `/v1` is inexpressible — and `/v1` is where vLLM,
llama.cpp's server and LM Studio actually serve, all three named in the project's own tech-stack
document. Separately, an unauthenticated local OpenAI-compatible server cannot bind at all,
because the OpenAI binding demands credentials the schema has no unauthenticated way to supply
(reproduced live: `could not bind 'openai:qwen3:32b': Missing credentials`). Together these mean
there is currently **no working configuration for a local OpenAI-compatible server**. And
`test_engine_adapter.py` exercises `openai_compatible` only at the provider-string level (line
175) — no test binds one, which is very likely why neither failure was noticed.

Plan 03-08 documented the path limitation rather than silently appending a suffix, and that was
the right call on the hidden-behavior axis. This plan keeps that principle and removes the
limitation: the path becomes something the user **declares**, validated at load, appended
verbatim, never guessed.

Purpose: one of the three providers SC#2 names is unusable, and it is the one with zero
binding-level coverage.

Output: `endpoint_path` and `endpoint_unauthenticated` on the profile schema, a `path` field and
a `url()` method on the shared `paaf_core` `Endpoint`, and the first tests in the repo that bind
an `openai_compatible` profile — with the control proving the no-auth declaration is load-bearing
rather than decorative.
</objective>
