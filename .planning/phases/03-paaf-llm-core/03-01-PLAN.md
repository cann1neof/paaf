## Phase Goal

**As a** self-hoster who does not want to write code, **I want to** name my own models in one YAML tree — each with a plain-language description of what it handles and the peers it may later hand off to — **so that** I own and can read the assistant's model configuration, and the mesh Phase 4 builds has validated data to traverse.

<objective>
Extend the config surface with the Phase-3 model-profile schema: named `ModelProfile`s and the `LlmConfig` root that holds the base prompt, the active profile, the ordered fallback chain, and the profile map — including the inert capability-manifest + peer-graph seam (MODEL-05/D-07) that Phase 4 makes live. This is the schema half of the phase's "it talks" slice: every other plan builds on these validated types. This plan also gives `paaf-llm` its first real dependencies (it was a deliberately dependency-free stub in Phase 2).

Purpose: MODEL-01 (named profiles, no code), MODEL-05 (manifest + peer graph as validated inert data), MODEL-06 (two LAN servers as distinct profiles) — the durable data contract the port, engine, and CLI all consume.
Output: `profiles.py`, `test_profiles.py`, and a `pyproject.toml` that declares the real framework dependencies + the `paaf` console script.
</objective>
