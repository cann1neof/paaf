<objective>
Build the encrypted secret store: API keys live in a separate encrypted file behind a pluggable `SecretStore` interface (D-04), never in the YAML tree, never logged, using audited crypto from pyca `cryptography` (Fernet + scrypt) per D-01/D-02 — no hand-rolled crypto. It must work headless and offline with no account or cloud KMS (D-03, PRIV-01/PRIV-02). This is the SC#3 secrets half. Because the master-key provisioning source is a durable on-disk contract the research explicitly flagged for ratification (Open Question 2 / A2), the plan opens with a decision checkpoint.

Phase Goal (developer-as-user story): **As a** privacy-minded self-hoster, **I want** my API keys stored encrypted and separate from my config, never printed to a log, **so that** I can run and verify the assistant without trusting it with my keys in plaintext.

Purpose: CORE-04 is a founding privacy commitment; getting the interface and the not-in-YAML/not-in-logs guarantees right now makes offline verifiability real from the first commit.
Output: `SecretStore` interface, a Fernet-backed encrypted-file implementation, and tests proving round-trip + absence from YAML and logs.
</objective>

  <name>Checkpoint: Master-key provisioning source for the encrypted secret store</name>
  <decision>Master-key provisioning source for the encrypted secret store (RESEARCH Open Question 2 / Assumption A2)</decision>
  <context>
CORE-04 requires the secret store to be separate + encrypted + write-only over the API + not in YAML + not in logs — it does NOT mandate how the master key is provisioned. The ship target is a headless, auto-restarting Linux service (D-03). The provisioning source is a durable contract downstream phases inherit, so it is decided deliberately, not defaulted. Crypto library is already fixed to pyca `cryptography` (Fernet + scrypt) per D-02 (audit history is the primary criterion); this decision is ONLY about where the master key comes from.
  </context>
  <options>
    <option id="key-file-0600">
      <name>0600 key file (from env var or systemd credential)</name>
      <pros>Headless auto-restart works with no human at boot; simplest UX; matches RESEARCH A2 v1 recommendation</pros>
      <cons>Key at rest on the same box; protection is filesystem permissions + disk encryption, not a passphrase</cons>
    </option>
    <option id="passphrase-at-boot">
      <name>Passphrase entered at service start</name>
      <pros>Strongest — master key never at rest on disk</pros>
      <cons>Breaks unattended restart on a headless box; needs an operator or a secrets manager at every boot</cons>
    </option>
    <option id="systemd-credential">
      <name>systemd credential (LoadCredentialEncrypted)</name>
      <pros>OS-managed, encrypted at rest, unattended restart; good headless fit</pros>
      <cons>systemd-specific; the Linux service itself is Phase 9, so this is forward-referencing</cons>
    </option>
  </options>
  <action>Present the three provisioning-source options to the developer and block until one is selected. Record the selection in the plan SUMMARY so Plan 08 can cite it in DECISIONS.md, and implement Task 1's `EncryptedFileSecretStore` master-key loading against the chosen source. If no response and the run is unattended, default to `key-file-0600` (RESEARCH A2 v1 recommendation — env var or 0600 key file) and flag the default in the SUMMARY for later ratification. Do NOT hard-code a master key into source or into the YAML tree under any option.</action>
  <verify><human-check>Developer has selected a provisioning source (or the key-file-0600 default is explicitly recorded), and the choice is written to the SUMMARY.</human-check></verify>
  <done>A master-key provisioning source is selected and recorded; Task 1 implements the store against it.</done>
  <resume-signal>Select: key-file-0600, passphrase-at-boot, or systemd-credential (the SecretStore interface keeps the others addable later)</resume-signal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| secret value → config YAML | a secret leaking into the config tree breaks CORE-04 (V7) |
| secret value → logs | a secret in a log line is an Information Disclosure |
| master key → disk/boot | how the key is provisioned is the real threat surface (checkpoint) |
| store → network | any account/cloud/telemetry call breaks PRIV-01/PRIV-02 |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-11 | Information Disclosure | secret in YAML/logs | high | mitigate | separate encrypted store; not-in-YAML + not-in-logs negative controls (V7) |
| T-02-12 | Information Disclosure | hand-rolled/misconfigured crypto | high | mitigate | pyca cryptography Fernet + scrypt only (D-02); no primitive assembly |
| T-02-13 | Information Disclosure | master key at rest | medium | mitigate | provisioning source decided at checkpoint; 0600 file / systemd credential; documented in DECISIONS.md |
